## Behavior ledger

- Focus: `focus()` is a support command for all classes, costing 1 AP and restoring up to the canonical `FOCUS_MP` (3) without exceeding max MP, once per turn. It provides no HP or guard. Validate MP in executed command order, including the adventurer refund: earlier focus may fund a following skill, later focus cannot pay earlier costs. Full MP at the focus action, repeated focus, resource/AP/lesson errors reject the entire plan unchanged and identify the actual command. SkillBook keeps its resource-gated offensive choices; advanced focus-before-skill combinations can be written directly and checked through the existing preview. No inserted action auto-submits or rewrites loop counts.
- Execution highlight: engine events carry only a transient executed-action index; App joins that index to the successful Python trace/source, outside SaveGameV1. Editor decorates the real source line at scene beats, including alias/function/loop calls, without changing selection, focus, scrolling, code or Undo history. Check plan and invalid runs never highlight playback. Contact keeps the corresponding player's line; enemy responses and completion clear it. Editing invalidates evidence for the rest of that playback even when the original text returns. Navigation/import and motion-preference disposal release it without replaying the committed turn. Skipped commands after victory never receive a highlight.

Six short boss reviews live in `content.ts`. The latest user request sets Grade 10 beginner difficulty: prompts use at most two short sentences, each ordinary task has one main idea, later tasks have scaffolds, and bosses do not combine three advanced concepts. The legacy `SOURCE_` exports and `LessonContract.sourceExercise` IDs now identify the active new curriculum; they do not bind the former source prompts. Validate each stated input, operation, output and executed data dependency; temporary computed variables and equivalent syntax remain valid. Exactly one offense is required in ordinary rooms, with optional support within 3 AP. Bosses keep small open concept contracts. Run and Check plan share validation and invalid plans preserve the checkpoint. Stable encounter IDs preserve completion, stars, rewards and drafts; old drafts may need editing. See docs/SOURCE-CURRICULUM.md and docs/BOSS-CHALLENGES.md.

- Sequence lesson: room 1-3 requires three executed print calls producing 3, 2 and 1 on separate lines before one power-1 offense. Room 1-1 prints Moon Gate with any equivalent argument form; room 1-2 combines a comment and the short message Light. Generic sequence evidence for bosses remains open. AP counts combat costs separately from Python print calls.

- Offensive power: attack and all skills accept optional integer power 1–3, defaulting to 1 for old calls. Each level above 1 adds 4 base damage before existing multipliers and armor, without changing AP/MP costs. New inserted offensive calls use explicit `(1)`; changing a command name preserves its argument expression and Undo history. Support commands remain argument-free. Ordinary exercises require an explicit power expression and one offense; practice variables do not alter real combat resources. Actual evaluated power is transient in GameAction/trace/events and shown through the existing log, forecast, AP, editor and scene owners. APBudget row.command now contains a complete call. SaveGameV1 remains unchanged and old drafts are preserved, though they may need editing for the new missions.

- Applied lesson evidence: an `if` branch must actually control a combat command, including calls through functions/aliases and a selected `else`; unrelated prints or a command after the branch do not qualify. Method evidence requires an executed bound instance method, including inherited methods and saved method aliases. Collection evidence records the actual receiver of a successful subscript or the actual argument to builtin `len`, including function parameters, aliases and slices; nested collection names inside string operations do not qualify. Native evaluation order and user attribute hooks remain intact. Bosses use the composed per-turn contracts in docs/BOSS-CHALLENGES.md; prior completions/rewards and drafts survive, while an older draft may require more concepts before its next valid turn.

- Battle HUD: the existing player CombatMeter shows current/max MP and a blue mana bar directly under its HP track, synchronized with `visibleBattle` during playback and the committed checkpoint after reload. Its accessible meter exposes the same real value, uses a zero fill for empty/zero-capacity mana and does not add motion. This is a read-only resource value; skill controls and their MP display stay beside the editor. The enemy meter receives no invented MP value.

- Multiple class skills and AP evidence: [docs/SKILLS-AND-AP.md](docs/SKILLS-AND-AP.md) records the user's accepted scope and domain rule. `src/skills.ts` owns nine definitions (three per class), names, costs and effects. SkillBook extends its existing right-column/dialog owners with four offensive choices (normal attack plus three skills), followed by support. Editor derives the exact skill from Python command references and switches them as one Undo operation. Insufficient MP blocks only the affected choices; legacy `skill()` keeps its original effect and cost. TurnPreview and Scene use the same skill names/icons, while engine owns damage, armor piercing and interruption. An interrupted counter cannot apply fresh poison; existing poison still ticks. No new save field or purchase is required.
- AP breakdown: Python records at most four executed command calls with source lines and active caller-loop lines, including the rejected fourth call. `actionBudget.ts` groups this bounded trace. PythonFeedback extends its existing inline surface with a native disclosure: collapsed for ordinary results, open for excess AP, showing actual call count, AP per call, first over-budget line and line/loop jump controls. Limited traces say “อย่างน้อย”; repeated calls get a resource-based count suggestion, never an automatic source rewrite. Runtime/engine errors still use the canonical diagnostic and editor line mark. Editing clears stale evidence. Run/Check plan share this validation and preserve the complete checkpoint on rejection.

- Initial Python download: allow up to 240 seconds for the self-hosted runtime on a slow first connection; this timer is separate from the 3-second code-execution limit. While loading, navigation/settings remain usable and combat is not submitted. A stuck load still exposes the existing Retry action and preserves the exact draft/checkpoint. This budget avoids the premature 60-second failure reproduced in the isolated, uncompressed slow-origin audit; it is not a promised real-device loading time.

- Offline installation and updates: App latches the first successful Python startup, then useOfflineReady permits background registration. offlineSupport observes an already active or controlling release even before that point and disposes listeners on unmount. A complete update waits for all older controlled tabs to close; it never takes over a live old page or removes its lazy chunks. Settings explains how to activate a waiting update after saving. The worker reuses verified release/HTTP cache bytes, retries stale HTTP content from the network, and rejects incomplete installs. No update path changes IndexedDB progress or automatically reloads a draft.

- Run: validation and runtime result precede one atomic combat commit. Invalid Python, missing concepts, rejected AP/MP/potions, excessive output, cancellation and timeout preserve the complete combat checkpoint, gold and objectives. Editing still saves the draft. The legacy mistake field is retained unchanged for SaveGameV1 compatibility; it is never incremented or used for scoring. This follows the explicit original user requirement that invalid code cannot change combat state.
- Check plan: optional practice runs real Python and lesson/engine validation, but never changes the combat checkpoint, mistakes or resources. Show action order, submitted AP and predicted post-counter HP/MP/potions. A losing forecast warns before submission. “รันแผนนี้” uses the existing Run path and fresh validation; previews are never committed directly. Editing, navigation, stopping and a new run invalidate the previous forecast.
- Diagnostics: PythonFeedback is the single inline result owner directly after Run and before the skill panel. Use 16px correction/code text, preserve the reported Python line and expose its 44px focus/jump control ahead of stdout. A new offscreen error scrolls into view once without moving focus or reopening the editor keyboard; an open dialog suppresses that reveal, and closing it cannot replay an old reveal. Printed text has a separately labeled keyboard-scrollable frame capped at 224px, inheriting global scrollbars, with 128 print calls/8,192 text characters enforced in Python. Only the concise feedback summary is an atomic live region. Editing clears stale marks and feedback, including full-document replacement and Undo. Invalid line numbers do not crash the editor. Runtime cancellation preserves the draft and checkpoint for both Run and Check plan.
- Correction content: all 18 concepts have specific Thai next steps. Missing-concept guidance follows actual declaration/entry/return/type-use evidence and may point to a related original source line; absent or unreachable constructs never receive an invented line. Runtime index/attribute/key/value/overflow/recursion/tab errors retain the real Python kind, raw detail and traceback line alongside Thai guidance. Trusted game validation/action/output messages remain distinct from native Python value-conversion errors. Corrections never change grading, commands or combat and never choose the player's tactical action.
- Lesson hints: LessonHints owns the inline help inside the same right-column mission. Keep the first two concept/observation hints and use a neutral example at level 3, with a reading question, verified expected output behind a native initially closed disclosure and explicit transfer guidance. The sequence sample demonstrates print order and explains that the learner still chooses combat commands/AP. Code/Thai copy and controls are 16px; code scrolls inside its ink frame and touch controls are 44px. Back/close restore the existing trigger appropriately; the final trigger hides help rather than remaining a no-op. Navigation/import resets transient hint state. Hint/prediction interaction does not mutate any SaveGameV1 field, insert text, submit combat or reduce stars. Runtime feedback remains owned only by PythonFeedback. The journal's separately disclosed reference examples retain their existing behavior.
- Offensive choice: the user's revised rule is recorded in [docs/OFFENSIVE-CHOICE.md](docs/OFFENSIVE-CHOICE.md). SkillBook separates exclusive attack/skill choices from optional defense/heal support. Choosing an offense rewrites Python name references through the existing lazy Editor owner, preserving comments, strings, object methods and lesson structure, or adds one statement if no offense exists. Syntax errors or learner-owned attack/skill bindings refuse automatic editing with an explanation. Changes form one Undo step; code-derived selection survives Undo/manual edits/reload without a new save field. Selecting a card retains focus; its confirmation focuses the editor without inserting duplicates. Loop counts are not changed automatically; skill is 2 AP and one use per turn. Actual executed actions are checked by the pure engine for mixed offense, so aliases cannot bypass the rule, while exclusive Python branches remain valid. Rejected Run/Check plan preserve the checkpoint and resources.
- Skill book (user request: add a skill selection screen): reuse Modal for focus containment and Escape. Inspect four actions and their current costs/effects without changing combat. Insufficient MP blocks choosing the skill; missing potions/full HP explain why support insertion is unavailable. Support insertion adds one complete Python statement after the cursor's current line, preserving indentation and all other draft text; native editor Undo restores it. The editor receives focus after insertion. Run still validates the lesson, AP and resources; preview never spends resources. Selection and insertion are gated during processing/playback, after combat ends and on a stale-tab conflict.
- Player tools layout (latest user request: group all user controls with code on the right, keep other information separate): SkillBook's `player` variant, MP and potions belong in the coding column after the editor workspace and its inline Python feedback. Enemy intent and battle history belong in the scene column. On phones these columns stack in that order. The panel shares ability definitions, previews and insertion with the full dialog. Cards and insertion are disabled during playback. Optional descriptions use the shared Modal; no overlay covers the stage during inline selection. The mobile Run bar is bounded by the editor workspace and is sticky only while that workspace has focus.
- Battle outcome: BattleResult is the single terminal-result owner in the right coding column directly after PythonFeedback and before the player tools. Mount only after committed combat playback finishes. Continue/retry, map and notebook actions precede the existing best/current stars, actual HP and shared StarRules. Use 16px Thai copy/buttons and 44px targets. Focus the outcome heading and reveal its primary action once, without reopening the editor keyboard or adding animation. An open Modal owns focus/scroll and consumes that automatic reveal; closing it cannot replay an old result. Tab from the heading reaches continue/retry first. Reuse App's existing room entry, map navigation and notebook mutation; do not add a second result toast, change rewards/ratings or write a checkpoint from the component. A defeated player retries the same room with their original draft and existing gold. Battle rules and the atomic reward commit remain independent of focus or rendering.
- Playback: the engine's committed checkpoint persists immediately. A disposable presentation copy updates HP at contact and MP/potions at the action beat. Run and its keyboard shortcut cannot submit a new turn during playback; editing the next command remains available. Results appear after the defeat beat. Navigation or a motion-preference change releases the presentation copy and retains the committed checkpoint.
- Battle audio: BattleAudio is the single optional audio owner, using SaveGameV1.settings.sound and both existing toggles. New games are muted. Unlock the shared AudioContext in the actual player gesture, before awaiting Python; never unlock or sound a Check plan. Attacks stay silent during anticipation; the existing paired hurt beat carries the source so class sounds start at contact. Guard/heal/charge/result have their own short cues. Invalid code emits no sound. Mute/navigation/hidden-page/unmount close the context and cancel all scheduled voices; motion changes stop the old presentation without replay. Ended sources disconnect, and suspended/unavailable audio is skipped without delaying or changing a turn. Disposed timelines cannot emit queued beats. Sound and reduced motion remain independent; no new save fields or external media are required.
- Tactics: boss stage is derived from the same HP thresholds that select move patterns, with no new save fields. The left enemy panel explains heavy/guard/charge/poison responses and labels the current counter during playback. Poison duration belongs with right-side player resources, changes at contact, and includes the fact that defense and potions do not remove it. Ended fights show win/retry text instead of an obsolete next intent.
- Cancel, timeout, navigation: invalidate request identity, terminate running worker, preserve code and combat checkpoint.
- Tool loading: the shell remains navigable while the scene loads; editor code loads only on room entry. No turn can submit until both tools are present. Leaving a loading room preserves it for resume. Module failure recovery explicitly persists the latest save and then reloads (failed dynamic imports are browser-cached); persistence failure or stale-tab conflict keeps the page open and exposes export/recovery feedback. Pointer interaction focuses execution buttons without a scroll jump, preserving the workspace's bounded sticky Run bar in WebKit.
- Back to map: keep drafts and active battle; selecting that active room resumes its existing checkpoint.
- Retry lost room: new HP/MP, retained draft, no gold loss. Won rooms may replay but never duplicate their first-clear reward.
- Victory/replay score: award 3 stars above 60% remaining HP, 2 above 30% through 60%, and 1 for a victory at or below 30%. Use integer cross multiplication for exact boundaries; code errors, hints and the legacy mistake counter carry no penalty. StarRules derives the current hero's exact integer HP bands from the same engine thresholds and exposes one native disclosure in the active mission or won result. Results show actual final HP and distinguish this run from the saved best. Preserve the maximum stars per room, including old saves. Gold/completion are first-clear only, while potions and the battle checkpoint reflect the replay. Completed campaigns show a derived recap and recommend a room with missing stars; journal and export use their existing owners and never reset progress.
- Learning journal: LearningJournal extends the same Modal owner with local Thai/English concept search and a completed-only filter. Its 18-lesson progress excludes six bosses explicitly. Open the current chapter by default; search results expand matching chapters, and empty results offer a clear reset. Own code comes only from the existing saved draft and is labeled unverified, independently of room completion. Reference examples require an explicit disclosure. CodeExcerpt owns read-only draft/example display and clipboard actions with inline status, exact indentation and honest manual-selection fallback. Browsing/copying never writes the active editor or commits combat. Notes retain their canonical SaveGameV1 field, debounce/persistence/export and 32,000-character limit; closing resets search only. Long source scrolls within its own 16px code frame at phone widths.
- Map framing: bottom-align the existing scene image with uniform cover scaling, protecting actor heads/feet from the crop. Put the chapter/location label in its own strip above the artwork, including long Thai names; it cannot cover characters. Maintain reserved image dimensions across chapter switches. Battle layout, animation timing and reduced-motion behavior retain their existing owners.
- Save: local IndexedDB; explicit saving/saved/failed feedback. Drafts debounce; committed combat changes persist without a draft delay. Conflicting tabs pause writes and request reload.
- Inventory: `engine.commitBattle` consumes only the potion delta from the active room. Potions bought while a room is in progress remain reserved for the next room; a turn, defeat, victory or replay reward cannot discard that reserve. Shop and empty-potion guidance state when purchases become usable.
- Save consistency: import/load reject non-string encounter/status/intent keys, missing heroes in battles, zero turn/attack, impossible HP/status combinations and battle potions exceeding total inventory. Imported shape checks run before replacement. IndexedDB writes compare against the last successfully loaded/persisted revision in the same transaction; rapid local edits cannot outrank another tab's actual commit. Broadcast comparison starts only after loading a baseline so an identical startup notification cannot falsely lock the page. Stale tabs must reload before import or reset. Invalid existing saves remain blocked until explicit recovery.
- Python isolation and printing: each evaluation receives a fresh public `math` module namespace. Changing a module attribute cannot affect another run. `print` respects Python `sep`, `end`, `None` defaults and `flush`; output limits include terminators, remain fatal to the turn even if caught by learner code, and use at most 128 rendered blocks with embedded newlines preserved.
- Save feedback identity: every mutation updates the canonical save ref and pending status synchronously, so a changed checkpoint cannot render with the previous “saved” label while its passive persistence effect waits. A completed older queue item cannot announce that newer pending edits are saved. Only the exact current checkpoint can set the saved status. Conflicting tabs show stopped-save feedback, including after local settings edits, and cannot overwrite the newer stored settings. DOM-first-render, delayed-completion and actual two-tab/reload browser regressions cover these cases.
- Offline update: build identity depends on file contents and worker logic, not the build time. Verify SHA-256 before reusing a cached response or storing a fetched file. Install into a separate cache; promote only after every asset succeeds. An incomplete update preserves the working previous version and IndexedDB progress. Activation removes only prior RuneCode caches, preserving unrelated caches. The background offline cache may download deferred modules before they are executed.
- Offline-ready feedback: useOfflineReady follows a complete active/controlling worker, including while register() waits behind a newer install. Installing or failed first releases cannot announce readiness. Observe subsequent worker/controller transitions and remove listeners on unmount. An incomplete update keeps the previous complete release ready and playable; the indicator does not promise that the browser will never evict local data.
- Import: validate before confirmation and replacement. Invalid file never changes current save. Export works even when IndexedDB is unavailable.
- Reset: app-owned dialog, safe action first, explicitly labels loss of local progress. No native confirm/alert.
- Modal: native dialog showModal provides focus containment and background isolation; Escape closes, focus restores to trigger.
- Dialog entry focuses the actual trigger explicitly before showing the same Modal owner, including Safari pointer activation. Editor document synchronization completes before paint and each whole skill insertion has its own Undo group; stale prop effects cannot restore a command after Undo.
- Mobile: all navigation remains reachable; editor action bar responds to visual viewport changes; snippet toolbar has touch/keyboard equivalents and opens the same skill book as the diorama launcher.

## Hero passives

The user-approved class distinction is specified in [docs/HERO-TRAITS.md](docs/HERO-TRAITS.md). `heroTraits.ts` owns parameters and Thai descriptions; `engine.resolveTurn` owns all effects. Combo and focused-spell preparation reset every turn. Knight restoration occurs only after a surviving, actually reduced counter and cannot fund an earlier action. Passive feedback in `CombatEvent.trait` is transient; SaveGameV1 is unchanged. Invalid plans and read-only previews preserve the checkpoint.

`HeroTrait` is the single native disclosure owner inside both SkillBook variants. It starts collapsed, has a 44px keyboard/touch summary and inherits the current ink/parchment palette. It never changes a draft or saved state. Existing TurnPreview displays only actual passive event messages; editing or navigation clears them with the owning forecast. Existing scene cues show combo/empowerment on the action beat and knight MP restoration at counter contact, including reduced motion. No extra dialog, continuous effect or separate turn state is introduced.

## Runtime token mapping

Python combat variables remain turn-start snapshots. Queued focus changes engine MP in command order after the complete run passes validation; it does not rewrite Python's `mp` variable during evaluation. Execution highlighting illustrates the committed animation, not a step debugger for arbitrary Python expressions.

DESIGN.md mirrors the canonical src/styles.css tokens. Phaser's art-only palette is intentionally independent of accessible DOM UI colors. A scene change cannot own combat or saved state.
